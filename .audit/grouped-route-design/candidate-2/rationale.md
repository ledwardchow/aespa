# Grouped-route test reachability

## Problem

Grouping currently decides both which pages are visited and which exact URLs survive into the scan. `RouteSampler._member_identity` drops queries for path groups, and `crawler.py` removes held links before `_record_page_intelligence`, which also caps DOM links at 300. The recon projection overwrites access by route, grouped coverage takes the best child status, and specialist handoffs drop query values from their scope. A similar layout is useful for crawl scheduling and display, but says nothing about an object's access rule. The design keeps sampled page work small while retaining exact targets, actor provenance, and truthful test outcomes.

## Usage (caller's view)

See `README.md` first. Its four calls are the contract. The crawler records links before sampling, then records actual fetch observations separately. The scanner pages exact targets by ID, selects a bounded set of tests with positive baselines, and sends requests through existing scope and policy checks. Specialist dispatch claims an exact scope and an immutable evidence token. None of these calls creates a `CrawledPage` merely because a link was seen.

## Shape

**Option A - dedicated exact-target catalog (chosen).** Add `DiscoveredTarget` with `(test_run_id, exact_url_key, state_key)` unique and the raw URL retained. The key may lowercase scheme and host after URL validation, but must leave path, raw query, repeated keys, empty values, and meaningful SPA fragment in order. The `route_pattern` is a separate display label. Add `TargetSighting` with a unique key over target, source page/state, observing credential, source kind, and interaction ID. Add `TargetAccessObservation` for a direct fetch of that same target under one actor. It stores `reached`, `denied`, or `unknown`, source page/traffic IDs, and a content fingerprint. An absent row means unknown. Seeing a link creates only a sighting. A response classification needs direct evidence; a fetch that ended in an ambiguous shell/error stays unknown.

`TargetCatalog` owns writes and keyset reads. `record_discoveries` commits each bounded batch before the sampler can discard held items. Its per-row unique constraints and SQLite upsert make retry and concurrent phases converge; a transaction rolls back the whole batch on failure. Nullable state, actor, and interaction values use a non-null encoded key or a `COALESCE` unique index, because ordinary SQLite `UNIQUE` does not deduplicate `NULL`. Each direct fetch has an immutable event key derived from its traffic ID or crawl observation ID, so a retry neither overwrites evidence nor creates duplicate observations. Source text is capped for display, but URL identity is never truncated. The API reads with `WHERE ... ORDER BY id LIMIT ...` and a cursor; all filtering happens before limit. This replaces the current 1000-row read-then-filter inventory path. The catalog does not impose a 300-link cap, though a documented run-size guard may stop recording with an explicit truncated-inventory status rather than silently lose links. The sampler can still use its own snapshot for queue control. Change `_member_identity` to include the full target identity even in path groups so distinct queries can be released or sampled independently; the route pattern still groups them visually.

Recon joins access facts by exact target, state, and actor, then summarizes each route as a set of observed object/identity pairs. It never overwrites one object with another or compares response text across different concrete URLs. `anonymous`, `authenticated`, `mixed`, and content equivalence are summaries only where the same exact target has comparable direct observations; otherwise classification is `unknown` or `mixed_unknown`. Ownership is not inferred from link visibility, successful access, or missing access. `_web_route_obligations` receives that evidence-limited summary, so one public object cannot erase an authenticated observation on another object.

Coverage keeps `PageOwaspTest` for actually visited/replayed pages and their distinct interactive `state_key`. Route rows may show a compact aggregate, but aggregate status is unresolved if any selected underlying page/category/class cell is unresolved; a finding remains visible separately. Standard completion uses raw applicable page/class cells plus explicitly selected target obligations, not `column_totals` from display groups. The two Standard completion reads in `scanner.py` and the frontend's totals/column display use the same raw-progress summary; the grouped row remains a display unit. Full already uses raw gaps and gets the same selected obligations. Neither mode adds every discovered URL to its denominator. A scan request to a different object does not inherit a representative page's covered status through `_match_page_for_url` or `resolve_web_page_id`; its concrete traffic and evidence attach to a selected `ScanObligation` or remain unclaimed, while `page_id` is used only for an exact URL or explicit interactive state. Existing source/replay page attribution may still point to the page that initiated a probe, but it cannot stand for the probed object's coverage result. Arbitrary mutated payloads do not create coverage pages. Direct scan probes do not manufacture a crawled-page row.

`select_idor_tests` starts from positive direct observations on concrete object URLs and configured identified sessions. It picks at most 80 targets and three other actors per target, using existing scan budgets and stable route/target ordering to spread the sample across groups. Link sightings without a positive fetch do not qualify. It persists only the selected tests as `ScanObligation` rows with exact target ID, owner/other actor IDs, baseline observation ID, and a unique selection key; `ProbeExecution` and `CoverageEvidence` remain the result records. An unobserved actor is a candidate for comparison, not known unauthorized. A finding requires a successful cross-account response that matches the same target's positive baseline and survives the validator; an absent result, denial-like shell, or incomparable content is inconclusive, not proof of denial. Re-running selection upserts the same obligations. It cannot create an N-squared account/object workload because target and actor limits are enforced before writes.

Specialist scope uses exact URL, `state_key`, attack class, parameter, and actor identity or IDOR owner/other pair. The active conflict query uses that same key. A fingerprint also includes an immutable evidence token. Same scope and token returns the existing row; different evidence after terminal status can create a new row. New evidence while a handoff is active is kept as an unclaimed lead and retried after termination, never dispatched concurrently for the same scope. A changed rationale alone is not new evidence. This avoids permanent route suppression and repeated duplicate probes. Both claim and active-conflict checks run in one transaction with a unique index, handling simultaneous Team/specialist callers. Existing `run_kind` filters remain mandatory for shared run IDs. API handoffs use the same exact scope rule.

The public surface is small for the work it hides. Callers submit discoveries, fetch observations, bounded selection, and exact specialist claims. They do not perform URL keying, provenance merges, coverage bookkeeping, or conflict checks. The catalog stores separate facts because these have different meanings; a nullable union row would make invalid states easy to construct. This follows `principle-model-the-domain`, `principle-boundary-discipline`, `principle-make-operations-idempotent`, and `principle-separate-before-serializing-shared-state`.

**Option B - append-only target fact journal.** Add one `TargetFact` table with immutable events: `link_seen`, `fetch_reached`, `fetch_denied`, `fetch_unknown`, `selected_test`, and `test_result`. A `(run_kind, run_id, event_key)` uniqueness constraint deduplicates events. Every event carries exact URL, optional state, source page, actor, traffic ID, and typed payload. The crawler appends all raw eligible links before `RouteSampler.offer` and changes `_member_identity` to retain exact query and fragment identity, as in Option A. The read side folds facts into route inventory, per-target access, and selected-test state; a cursor serves facts and a separate aggregate cursor serves targets, so the current 1000-row prefilter cap disappears. Recon groups folded access only after matching exact URL, state, and actor. The selector emits at most 80 positive-baseline object tests and three alternate actors per object into selected-test facts. Scanner completion folds these selections alongside raw page cells, while route rows retain an unresolved status if any selected child is open. Exact traffic evidence remains separate from source/replay page IDs, and arbitrary probes do not create pages. Handoffs still need exact-scope and evidence-token changes as in Option A. Archives serialize the fact stream and replay it under remapped page, credential, and traffic IDs; v1 imports have no facts. Its main advantage is a clear immutable history and easy merge of concurrent crawl actors. Its cost is a larger read projection and a tagged payload where each event kind permits different nullable fields; a simple caller has to trust a more complex event-folding layer. It may be attractive if AESPA later needs to audit every discovery transition, but that is beyond this fix.

## Synthesis decision

Choose Option A. The indexed target, sighting, and fetch records directly serve the dominant reads: browse exact targets, find a positive baseline for one object, and summarize route access. The journal makes those reads depend on a fold and cache invalidation. Option A keeps one owner for each invariant and only adds rows for facts AESPA already needs. Retain Option B's append-only discipline for access evidence: old observations are never overwritten to make a later actor's result appear authoritative.

## Persistence and archive reconciliation

One Alembic migration creates the three catalog tables and indexes, adds exact-target/actor/baseline references plus a unique selection key to `ScanObligation`, and adds exact-scope/evidence columns and unique constraints to `SpecialistHandoff`. Keep the existing broad `canonical_url` only as a display/search field; stop using it for duplicate or conflict decisions. Migrate old handoffs from their stored `target_url`, `parameter`, and session label to exact scope. Give legacy terminal rows a legacy evidence token scoped to their row ID so they cannot suppress later concrete evidence; keep active rows exclusive for their exact scope until they finish. This migration must account for old nullable actor labels and rows without a parseable target. No historical discovery rows are synthesized from `route_groups_json`: those URLs were never retained.

Upgrade crawl archive format from v1 to v2. Export targets, sightings, and direct observations with source page URL plus `state_key`, credential username, and traffic archive identity so import can remap IDs. The current archive's page URL fallback is ambiguous for same-URL interactive states; v2 uses the state key first and preserves exact URL if a source cannot map. Validate target and provenance types and scope on import, upsert under destination run ID, and rebuild recon and selected work only from available evidence. Accept v1 with empty new collections. Do not infer missing URLs or access outcomes from group counts. Add API schemas only for a cursor-based target-inventory response and any displayed access provenance. No new runtime asset is proposed, so PyInstaller bundle lists need only be checked for the Alembic revision already included by existing rules.

## Tradeoffs accepted

- We accept three narrowly keyed tables in exchange for direct, indexed reads and distinct meanings for discovery and access.
- We accept a bounded IDOR sample in exchange for predictable request cost; an unselected object remains available to the lead for a manual or evidence-driven test.
- We accept `unknown` in route access and IDOR outcomes when direct evidence is missing in exchange for avoiding false denial and false coverage claims.
- We accept an archive version change and an Alembic migration in exchange for durable, remappable provenance.

## Alternatives considered

Using `TargetIntelItem` as the catalog would keep schema changes small, but its current URL value cap, 300-link producer cap, check-then-insert dedupe, and 1000-row read path would all need special rules. More importantly, its generic `kind`/metadata fields expose access and selection semantics to callers. Extending `PageLink` alone also fails because it records graph edges only after target page creation today and has no direct fetch or actor outcome. Both shapes expose more policy than the dedicated catalog hides.
